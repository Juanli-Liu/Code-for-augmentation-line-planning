# 第四阶段：必然触发加割换方案的算例

本目录的 8 个 CSV 是独立输入，不依赖、不覆盖旁边的 Data。未修改生产模型或求解逻辑，也没有预先注入冲突割。

本例验证完整流程：首轮唯一选择候选 0 → 第一层证明不可行 → 自动加入 x_0 <= 0 → 第二轮唯一选择候选 2 → 第一层可行。

## 数据规模和设计

- 4 个车站 A、B、C、D，5 个有向区间，8 条站内轨道。
- 规划时域 [0,70]，每步 1 分钟；始发前、终到后各占轨至少 15 分钟。
- 中间停车至少 4 分钟；起车附加 2 分钟、停车附加 3 分钟。
- 1 趟既有上行车 E0：C→B→A，在 t2 轨道停车，实际时刻 15→30/34→49；后移上限为 0。
- 1 个新增 OD：A→C，共 100 人。
- 两条下行候选线路，可选频率只有 1。long 座位数 100、备用数量 1；short 备用数量为 0，由工作量约束禁止选择。
- 下行 A→B、B→C 区间容量均为 1，两条候选不能同时开行。上行既有车使用独立有向区间和 t2 轨道。

| 候选内部编号 | 线路业务 ID | 编组 | 路径与停站 | A→C 旅行时间 | 最短整趟在途时间 |
|---|---|---|---|---:|---:|
| 0 | 0 | long | A停—B通—C停—D停 | 25 | 49 |
| 1 | 0 | short | 同上，备用数量为0 | 25 | 49 |
| 2 | 1 | long | A停—B停—C停 | 34 | 34 |
| 3 | 1 | short | 同上，备用数量为0 | 34 | 34 |

候选编号按现有加载器的线路 ID、频率、long/short 顺序生成。候选编号不是手动输入的。

## 为什么首轮必选候选 0

线路 0 的运行时间：

- A→B：10 + 2 = 12；
- B→C：10 + 3 = 13；
- C 停站：4；
- C→D：15 + 2 + 3 = 20。

因此 A→C 旅客时间为 12+13=25，整趟 A→D 在途时间为 12+13+4+20=49。

线路 1 的 A→C 时间为 (10+2+3)+4+(10+2+3)=34。

未满足需求惩罚为 10×25=250 人均分钟。两种有效候选都能提供 100 个座位，因此三个主问题选择的目标分别为：

- 候选 0：100×25=2500；
- 候选 2：100×34=3400；
- 不开车：100×250=25000。

区间容量禁止两者同时选中，另外两种 short 候选因备用数量为 0 不可选。所以首轮最优候选集合唯一为 {0}，不依赖求解器如何处理同目标解。

主问题的工作量只要求 49 <= 1×70，端点占轨时间在各站分别累计，因此它不会提前排除候选 0。这符合主问题仅提供聚合必要条件的设计。

## 为什么第一层必然不可行

候选 0 的完整事件链需要：

    始发前占轨15 + 最短在途49 + 终到后占轨15 = 79 > 70

所有事件必须位于 [0,70]，不存在满足该事件链的时刻表。第一层因此应返回 ProvenInfeasible，而不是超时未定。

完整选中集合为 C={0}，协调器自动生成：

    sum(x_a, a in C) <= |C|-1
    即 x_0 <= 0

## 为什么第二轮换选后可行

候选 0 被割排除，候选 2 的目标 3400 小于不服务的 25000，故第二轮唯一选择 {2}。

候选 2 的完整事件链最短为 15+34+15=64 <= 70。例如以下新增车时刻合法：

| 车站 | 轨道 | 到达侧事件 | 出发侧事件 |
|---|---|---:|---:|
| A | t1 | 开始占轨 0 | 实际出发 15 |
| B | t1 | 实际到达 30 | 实际出发 34 |
| C | t1 | 实际到达 49 | 释放轨道 64 |

既有车使用相反方向的独立轨道，二者不产生同向冲突。第一层是零目标可行性问题，实际输出允许更长停站或占轨，不要求与上表示例完全相同。

## 运行与实际验收

从项目根目录运行实际 C++ 主程序：

    & ".\augmentation line plan\augmentation line plan\x64\Release\augmentation line plan.exe"

可执行文件位置以本机 MSBuild 输出为准。主程序读取 `main.cpp` 开头的 `kInputDataDirectory`，当前设为 Test_data_complex；若要单独运行本例，须将常量路径末尾改为 Test_data 并重新编译。主程序不读取命令参数。下方独立验收程序仍通过参数指定待验收数据目录。

当前统一验收入口是项目根目录的 `scripts/run_baseline.ps1`，无需改变主程序输入常量，即可通过生产模块分别以 MILP、SAT 验证本例的两轮闭环。下文首次输出保留作历史记录。

本目录 parameters.csv 的 planning_output_root 使用绝对路径，将两轮报告保存在本目录 results/run_* 下；搬移项目时需更新该字段。

main_run.txt 保存主程序输出。首次实际运行已取得：

| 轮次 | 选择集合 | 主问题目标 | 第一层判定 | 新增割 |
|---|---|---:|---|---|
| 1 | {0} | 2500 | 已证不可行 | x_0 <= 0 |
| 2 | {2} | 3400 | 可行 | 无 |

verify_iteration.cpp/verify_iteration.vcxproj 直接编译并调用正式数据加载、主问题、时刻表和迭代模块，使用真实 COPT；不使用 Python、不模拟求解状态。它断言两轮选择、目标、客流、不可行判定、完整集合割、第二轮可行与报告文件，并独立检查最终见证的时间域、活动时长和允许/固定轨道。

在 Visual Studio x64 开发环境中编译和运行：

    msbuild ".\augmentation line plan\Test_data\verify_iteration.vcxproj" /p:Configuration=Release /p:Platform=x64 /p:PreferredToolArchitecture=x64
    & ".\augmentation line plan\Test_data\build\Release\verify_iteration.exe" ".\augmentation line plan\Test_data"

验收输出保存在 verification_run.txt。每次验收也产生独立 results/run_*，不覆盖前一次报告。

本例专门通过端点占轨与时域矛盾验证加割闭环，不声称覆盖同向列车冲突、冲突核缩减或具体动车组交路。
